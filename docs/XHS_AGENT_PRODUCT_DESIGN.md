# 小红书运营发布 Agent 产品设计（完整方案）

> 注意：本文是早期 Agent 构想，不再作为内容审核与自动发布的实施口径。最新唯一方案见 [内容生产审核与云手机发布闭环-明确版.md](./内容生产审核与云手机发布闭环-明确版.md)。

## 0. 普通人介绍版（可直接复用）

### 0.1 一句话介绍

这是一个给小红书团队用的“内容工作台”，把创作、发布、复盘放在一个系统里，让大家发得更快、出错更少、数据更清楚。

### 0.2 30 秒介绍

以前做小红书内容，要在很多工具之间来回切：找素材、写文案、做图、定时发布、看数据。  
这个系统把这些环节合到一起，运营同学可以在一个页面完成内容生产和发布，系统还会在发布前自动检查常见问题，发布后自动回收数据做复盘。

### 0.3 1 分钟介绍（业务视角）

这个产品解决的是运营团队日常“重复劳动多、协同慢、复盘难”的问题。  
它不是只做 AI 写文案，而是把整个流程串起来：
1. 先根据历史数据给选题和发布时间建议；
2. 再辅助生成标题、正文和标签；
3. 发布前自动质检，避免低级错误；
4. 发布后自动回收互动数据，形成日报/周报。  

最终价值是：同样人力下，能更稳定地生产内容，更快迭代出有效选题。

### 0.4 适合对外展示的三大价值点

1. 提效：减少人工重复操作（找素材、改文案、排期、跟进状态）
2. 降错：发布前自动校验，减少内容和流程错误
3. 可复盘：数据自动汇总，知道什么内容有效

### 0.5 不夸大承诺（建议统一口径）

1. 这是“运营提效系统”，不是“完全自动代替人”
2. 关键发布动作仍可设置人工审批
3. AI 负责建议与执行辅助，业务决策仍由团队把关

## 1. 文档目的

为现有项目 `/Users/yyx/ztqc/web` 设计一套可落地的“小红书运营发布 Agent”产品方案。  
目标是在不推翻现有发布系统的前提下，把“人工重复操作”升级为“Agent 驱动的流程自动化”。

---

## 2. 背景与问题定义

### 2.1 当前系统基线（已具备）

当前系统已有以下基础能力：

1. 小红书发帖（立即发布 / 定时发布）
2. 帖子管理（编辑、取消、立即执行、删除、本地状态同步）
3. 云登环境管理与账号分配
4. 管理后台统计（发帖趋势、已发布列表）
5. AI 生图、文案、工作流等能力

### 2.2 业务痛点

1. 选题、起标题、配标签依赖人工经验，不稳定
2. 发布前质检依赖人工检查，容易漏（字数、禁用词、封面质量等）
3. “素材->文案->排期->发布->复盘”流程割裂，执行成本高
4. 多账号运营协同困难，排期冲突和重复选题常见
5. 复盘慢，难以形成可复用策略

### 2.3 产品目标

1. 提升单人运营产能（减少重复性流程操作）
2. 提升发布质量一致性（自动化质检）
3. 形成“数据驱动选题-发布-复盘”闭环

---

## 3. 产品定位与边界

### 3.1 定位

该 Agent 是“运营执行代理”，不是替代业务决策者。  
它负责建议、检查、执行、回写、复盘，关键决策仍由人审批。

### 3.2 边界（首版）

**Agent 负责：**
1. 选题建议与发布时间建议
2. 标题/正文/标签生成与优化
3. 发布前自动质检
4. 自动排期与冲突规避
5. 发布后数据回收与复盘建议

**Agent 不负责：**
1. 业务战略方向拍板
2. 高风险品牌公关决策
3. 越权直接发布（需遵守审批策略）

---

## 4. 用户角色与权限

### 4.1 角色定义

1. `运营专员`：日常创建内容任务、编辑、提交审批、触发发布
2. `运营组长`：审批关键内容、调整策略、查看组维度报表
3. `管理员`：账号环境分配、规则配置、全局监控、审计

### 4.2 权限矩阵（建议）

1. 运营专员：创建任务、调用 Agent 建议、提交待审批、查看自己数据
2. 运营组长：审批通过/驳回、调整排期优先级、查看组内看板
3. 管理员：配置规则、配置 Agent 策略、跨账号查看、操作审计

---

## 5. 核心业务流程（To-Be）

### 5.1 端到端流程

1. 运营创建“内容任务”（目标、人群、产品、时间窗）
2. Agent 生成候选选题（含建议标题、标签、封面方向、发布时间）
3. 运营确认后进入“内容生产”（文案 + 素材）
4. Agent 执行发布前质检并返回风险项
5. 通过质检后进入排期；若命中规则阈值则进入人工审批
6. 发布执行与状态跟踪（成功/失败/重试）
7. 发布后自动同步互动数据，生成复盘卡片
8. Agent 输出下一轮优化建议

### 5.2 状态机设计

建议新增统一任务状态：

1. `draft`（草稿）
2. `planned`（已选题）
3. `producing`（内容生产中）
4. `qa_failed`（质检未通过）
5. `qa_passed`（质检通过）
6. `pending_approval`（待审批）
7. `scheduled`（已排期）
8. `publishing`（发布中）
9. `published`（已发布）
10. `publish_failed`（发布失败）
11. `analyzing`（复盘中）
12. `closed`（已归档）

## 6. 功能设计（完整模块）

### 6.1 模块A：运营驾驶舱（Dashboard）

**目标：** 让运营团队每天先看“今天发什么、风险在哪、表现如何”。

功能点：
1. 今日待发布列表（按账号、时段、优先级）
2. 质检风险看板（待修复项、高风险项）
3. 发布执行看板（成功率、失败原因分布）
4. 内容表现看板（曝光、互动率、转化代理指标）
5. Agent 建议卡（今日推荐选题与发布时间）

---

### 6.2 模块B：内容任务中心（Task Center）

**目标：** 把“每条笔记”升级成可追踪任务。

功能点：
1. 创建内容任务（主题、目标、账号、计划窗口、优先级）
2. 任务列表（状态筛选、负责人筛选、账号筛选）
3. 任务详情（时间线、日志、操作记录、变更记录）
4. 一键调用 Agent 生成草案（标题/正文/标签）
5. 版本管理（草案v1/v2，支持回滚）

---

### 6.3 模块C：选题 Agent（Topic Agent）

**目标：** 将“拍脑袋选题”变成“数据驱动选题”。

输入：
1. 历史内容表现数据
2. 业务活动日历（促销/上新节点）
3. 账号定位与禁忌主题

输出：
1. 选题候选（优先级分层）
2. 每个选题的理由（参考历史表现和时效性）
3. 推荐发布时间窗

规则：
1. 同账号 7 天内选题去重
2. 命中禁用主题直接拦截
3. 低置信建议标注“需人工复核”

---

### 6.4 模块D：内容生成 Agent（Copy Agent）

**目标：** 标准化生成“可发布草案”。

功能点：
1. 标题生成（多版本）
2. 正文生成（风格模板：种草/测评/教程）
3. 标签生成（数量和热词平衡）
4. CTA 建议（评论引导、收藏引导）
5. 文案改写（缩短、增强口语化、品牌口径统一）

约束：
1. 标题 <= 20 字（符合当前后端校验）
2. 正文 <= 1000 字（符合当前后端校验）
3. 输出自动抽取 tags 并回填

---

### 6.5 模块E：发布质检 Agent（QA Agent）

**目标：** 在发布前自动发现问题，降低失败和违规率。

质检维度：
1. 结构校验：标题/正文/图片/标签完整性
2. 平台规则：字数、图片数量、疑似违规词
3. 品牌规范：禁用词、口径一致性
4. 素材质量：分辨率、比例、重复图检测
5. 体验质量：可读性、信息密度、标签相关性

输出：
1. `pass` / `fail` / `manual_review`
2. 问题清单（严重级别：P0/P1/P2）
3. 修复建议（可一键应用）

---

### 6.6 模块F：排期与执行 Agent（Schedule & Execute Agent）

**目标：** 让多账号发布自动排程、自动执行、自动重试。

功能点：
1. 自动排期（按账号时段、历史最佳窗口）
2. 冲突检测（同账号同时段冲突）
3. 执行策略（立即/定时）
4. 失败重试（可配置重试次数和间隔）
5. 异常升级（连续失败转人工）

执行规则（建议）：
1. `max_retries = 2`
2. 仅对可重试错误重试（网络/临时 API 异常）
3. 非可重试错误直接标记失败并告警

---

### 6.7 模块G：复盘 Agent（Insight Agent）

**目标：** 自动完成日报/周报和策略回流。

功能点：
1. 自动同步数据（点赞、评论、收藏、分享、浏览）
2. 指标看板（按账号/选题/标签/发布时间）
3. 表现分层（爆款、正常、低表现）
4. 原因归因（选题、文案、发布时间、封面）
5. 下轮建议（继续/调整/停用）

---

### 6.8 模块H：审批与风控中心

**目标：** 对关键节点可控，避免误发和违规。

触发审批条件（示例）：
1. 账号级高风险标签
2. 命中敏感词策略
3. 新人账号首发
4. 低置信内容（Agent 置信度低于阈值）

能力：
1. 审批通过 / 驳回 / 退回修改
2. 审批理由必填
3. 审批记录全量留痕

## 10. Agent 编排设计（无长期记忆前提）

采用“短会话状态 + 规则驱动 + 可回放执行”的模式：

1. `Plan`：根据任务状态决定下一步动作
2. `Act`：调用对应服务（文案、质检、发布、同步）
3. `Observe`：接收结果与异常
4. `Decide`：推进状态 / 重试 / 转人工
5. `Log`：写入 `agent_runs` 和操作日志

控制项：
1. `max_steps`（避免死循环）
2. `timeout_ms`（超时保护）
3. `idempotency_key`（防重复执行）

## 11. 非功能要求（NFR）

1. 审计：所有 Agent 决策可追踪（输入、输出、规则、执行人）
2. 可靠性：发布链路成功率目标 >= 99%（可重试场景）
3. 性能：单次草案生成 P95 < 8s（含模型响应）
4. 安全：RBAC + 敏感操作审批 + API 限流
5. 可观测：任务成功率、失败原因、Agent 调用耗时和成本

---

## 12. 核心 KPI

1. 人效：人均日处理内容任务数
2. 效率：从任务创建到发布完成耗时
3. 质量：质检拦截率、发布失败率
4. 结果：内容互动率、爆款占比
5. 稳定：异常转人工率、重试成功率

## 14. 验收标准（UAT）

1. 运营可在 3 分钟内完成“创建任务->草案->质检->排期”流程
2. 质检可拦截 95% 以上的结构性错误（空标题、超字数、缺图等）
3. 定时发布可用率达到现有发布模块同等水平
4. 审批链路可追溯：任一发布都可定位审批人和审批时间
5. 复盘报告可自动产出，且可追溯到帖子明细

---

## 15. 与现有系统对接建议

1. 直接复用已有 `xhs_service` 发布能力，不重写底层发布
2. 新 Agent 模块先作为“上层编排”，避免动核心稳定链路
3. 复用已有 admin 统计页面能力，逐步加入任务与 Agent 维度
4. 保持现有 RBAC 与数据隔离规范（见 `docs/DATA_ISOLATION.md`）

---

## 16. 风险与应对

1. 模型输出不稳定  
应对：规则先行 + 低置信转人工 + 模板化输出

2. 发布外部依赖不稳定（环境/API）  
应对：重试机制 + 降级 + 异常队列

3. 团队习惯迁移慢  
应对：先“建议模式”再“半自动”再“受控自动”

4. 审批负担过重  
应对：按风险分级审批，低风险自动放行

---

## 17. 首版建议（最小可用）

如果你希望最快上线，首版只做这 5 件事：

1. 任务中心（状态机 + 时间线）
2. 草案生成（标题/正文/标签）
3. 发布前质检（结构 + 禁用词 + 基础规则）
4. 审批节点（通过/驳回）
5. 发布后日报（自动聚合）

这样能在较低改造成本下，快速体现 Agent 的真实业务价值。
