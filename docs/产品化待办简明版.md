# 产品化待办总表（简明版）

完整系统思维导图和逐项任务拆分见 [全系统思维导图与产品化任务拆分.md](./全系统思维导图与产品化任务拆分.md)。

## 一句话目标

把现在公司内部使用的小红书内容和数据工具，改造成可以给不同公司独立开通、数据互不干扰、使用过程可追踪、费用算得清楚的正式产品。

## 一、目前到底有什么

| 模块 | 现在能做什么 | 当前判断 |
|---|---|---|
| AI 内容 | 生图、提示词、文案、素材、模板、车型图库、工作流 | 已经能用，但内部生图服务仍有概率性网络/上游错误，必须先完成稳定出口和任务核验 |
| 小红书数据 | 已搭建运营和投流两个看板 | 当前准确并可继续对账的是投流看板；运营看板还缺云手机完整采集链路，不能按完整准确数据交付 |
| 小红书发布 | 已有浏览器发布、定时发布和失败记录 | “内容生产 → 人工审核 → 云手机自动发布”闭环尚未完成 |
| 登录与设备 | 云登环境、手机验证码、二维码扫码 | 有原型，暂时依赖公司自己的电脑和手机 |
| 管理后台 | 用户、角色、账号分配、任务、模型配置 | 有基础，但还不是企业多租户后台 |

## 二、上线产品前的八个关键问题

| 问题 | 现在是什么情况 | 需要做到什么 |
|---|---|---|
| 多租户 | 没有，所有人仍在同一个公司空间 | 每家公司有独立空间 |
| 数据隔离 | 有用户和部门隔离，没有公司隔离 | 不同公司互相看不到任何数据和文件 |
| 角色权限 | 有 7 种角色，约 4 个权限层级 | 增加企业管理员，并把查看、发布、导出等权限拆清楚 |
| 审计日志 | 生图、同步等任务有记录，管理操作记录不全 | 能查到谁在什么时间改了什么、执行了什么 |
| 大模型 | 目前主要调用云端接口 | 保留云端，企业客户可选择自己的 Key 或私有模型 |
| 并发性能 | 生图支持排队，其他模块没有完整压测 | 测清可支持多少用户、任务和设备 |
| 备份导出 | 有手动数据库备份和部分 Excel 导出 | 自动异地备份，客户能完整导出自己的数据 |
| 计量计费 | 只能看调用次数，算不出每个企业真实成本 | 按企业统计图片、token、任务、存储和费用 |

## 三、总待办

## 目标 1：先确定我们要卖什么

| 小目标 | 现在 | 下一步 | 做完后的结果 |
|---|---|---|---|
| 第一版产品 | 功能很多，边界不清楚 | 第一版只主推“AI 内容工作台 + 小红书数据看板” | 销售和研发知道第一版交付什么 |
| 自动发布 | 已有单独的发布能力，但没有和内容生产、审核串成一条链 | 先完成“生产、质检、审核、云手机发布、结果回传”闭环；全自动作为可选能力 | 审核通过的正确版本才能被发布，且全过程可追踪 |
| 第三方接入 | 依赖公司自己的云登和手机 | 定义客户自带云登、账号、手机号和手机的方式 | 客户不再依赖公司共享登录资产 |
| 产品拆分 | 所有功能放在一个系统里 | 拆成内容、数据、采集、发布四个模块 | 每个模块可以单卖，也可以组合卖 |

## 目标 2：让不同公司可以安全使用

| 小目标 | 现在 | 下一步 | 做完后的结果 |
|---|---|---|---|
| 企业空间 | 只有用户，没有公司 | 增加企业、工作区和企业成员 | 可以给第二家公司单独开通 |
| 数据隔离 | 主要按用户和账号分配 | 所有业务数据和文件增加企业归属 | 两家公司数据完全看不到彼此 |
| 权限 | 角色固定、判断分散 | 明确企业管理员、负责人、运营、投手、只读权限 | 每个人只能操作被授权的功能和账号 |
| 审计 | 只有部分任务记录 | 记录登录、角色、分配、发布、导出、删除和配置变化 | 出问题时能完整追查责任和过程 |
| 密钥安全 | 部分第三方 Key 存在数据库里 | 加密保存，页面默认不显示完整内容 | 数据库泄露也不能直接拿走第三方 Key |

## 目标 3：把系统稳定性做好

| 小目标 | 现在 | 下一步 | 做完后的结果 |
|---|---|---|---|
| 任务中心 | 生图和部分同步已有任务记录，但未知状态、断点和失败恢复仍不统一 | 生图、采集、发布、报表、导出全部进入统一任务中心 | 重启或网络抖动后任务不会丢，也不会盲目重复执行 |
| 失败重试 | 部分同步任务能重跑失败项 | 所有批量任务都显示每项成功失败并支持单独重跑 | 用户不用找研发手工补任务 |
| 图片存储 | 仍有 Windows 本地文件依赖 | 图片、车型库、导出文件放到对象存储 | Windows 磁盘或隧道故障不影响历史图片 |
| 数据备份 | 主要靠手工备份 | 每天自动备份到另一处，并定期测试恢复 | 数据库损坏后可以恢复 |
| 监控告警 | 经常等页面卡死后才查日志 | 监控接口、数据库、磁盘、队列、云登和手机 | 问题发生前或发生时自动提醒 |
| 性能测试 | 没有正式报告 | 分别测试网页、看板、生图、同步、导出并发 | 能明确告诉客户系统容量 |

## 目标 4：把小红书数据和执行链路做成产品

两个看板不能使用同一个“已完成”口径：

- **小红书投流数据面板**：现有广告报表数据已经可以形成准确看板，下一步重点是多租户授权、监控、对账和 SLA。
- **小红书运营数据看板**：页面和指标已经搭好，但准确性依赖云手机完整上线后的账号主页、帖子、互动和客资采集。在全账号覆盖、每日增量、失败补采和连续周期对账完成前，只能标记为“数据建设中”。

| 小目标 | 现在 | 下一步 | 做完后的结果 |
|---|---|---|---|
| 投流数据准确性 | 当前已有准确数据和完整看板 | 固化源报表、事实表、聚合表和看板对账 | 投流数字可对外解释和下钻 |
| 运营数据准确性 | 页面已完成，但采集覆盖和连续性未验收 | 上线云手机采集、每日增量、失败补采和逐日对账 | 运营看板达到可交付的数据准确性 |
| 客户数据接入 | 主要使用公司云登环境 | 提供 Windows 客户端，让客户连接自己的云登环境 | 客户可以采集自己的授权账号 |
| 登录恢复 | 需要公司手机收验证码或扫码 | 登录失效时通知客户用自己的手机处理 | 不共享客户手机号和验证码 |
| 采集记录 | 部分任务已有批次和失败项 | 每次采集保存账号、时间、执行电脑、结果和截图 | 采集为空时能知道具体原因 |
| 账号采集策略 | 当前仍偏向一次任务抓一批账号 | 为每个账号保存全量/增量水位，拆分列表、详情和互动阶段，保存原始快照并只补失败项 | 不因排序变化、任务中断或解析失败漏采、重复采集 |
| 内容任务 | 工作流结果和审核发布目前没有串联 | 由已发布工作流批量生产内容项，保存来源、车型、图文和版本；独立 AI 生图继续保留 | 一条笔记从工作流生产到发布始终可追踪 |
| 机器预审 | 目前主要依靠人工发现问题 | 检查敏感词、事实与政策、图片文字、车型一致性、比例和缺图 | 明显问题在提交人工前被拦截 |
| 人工审核 | 还没有完整审批闭环 | 支持通过、驳回、填写意见、指定返工内容和再次提交 | 谁审核、审核哪一版、为什么驳回都能查到 |
| 发布流程 | 当前可直接创建发布任务 | 只有审核通过的内容版本才能排期和发布 | 防止旧版或未审核内容被误发 |
| 云手机发布 | 还没有接入正式链路 | 平台调用云手机提供的发布接口，由云手机在官方 App 中执行 | 发布执行端可以独立升级，不和内容系统绑死 |
| 结果回传 | 现有发布记录不够完整 | 云手机回传领取、执行、成功、失败、截图、帖子链接和错误原因 | 平台能看到真实进度并支持失败重试 |
| 发布后回收 | 内容生产与数据看板尚未闭环 | 发布成功后回查帖子并同步互动数据 | 能从内容生产一路复盘到最终效果 |

### 新增重点闭环：内容生产到自动发布

具体业务边界、状态、异常处理和云手机接口以 [内容生产审核与云手机发布闭环-明确版.md](./内容生产审核与云手机发布闭环-明确版.md) 为唯一口径。

```text
创建内容任务
  -> 选择工作流版本、事实来源、车型和目标账号
  -> 工作流生成标题、正文、标签和图片
  -> 机器预审
  -> 人工审核
  -> 不通过：带审核意见返工并生成新版本
  -> 通过：锁定审核版本并进入排期
  -> 调用云手机发布接口
  -> 云手机在小红书官方 App 执行发布
  -> 回传截图、帖子链接、成功或失败原因
  -> 发布后同步数据并进入复盘
```

完成标准：任意一条已发布内容，都能查到内容来源、生成版本、审核人、发布时间、执行设备、发布截图、帖子链接和失败重试记录。

## 目标 5：最后完成商业化上线

| 小目标 | 现在 | 下一步 | 做完后的结果 |
|---|---|---|---|
| 用量统计 | 只有任务次数和存储统计 | 记录每个企业的图片、token、工作流、采集和存储 | 知道每个客户用了多少资源 |
| 成本核算 | 不知道每个客户真实模型成本 | 保存不同模型和供应商的价格 | 能算出每个客户的成本和毛利 |
| 套餐配额 | 没有套餐 | 设置成员数、账号数、设备数、AI 用量和并发限制 | 可以做团队版、增长版和企业版 |
| 客户开通 | 管理员手动跨多个页面配置 | 建立试用、企业初始化、成员权限、资产接入、历史数据初始化和验收流程 | 新客户按清单开通并确认每项是否可用 |
| 域名 HTTPS | 当前还是 HTTP | 正式对外前配置域名、HTTPS 和安全入口 | 客户登录和数据传输受到保护 |
| 客户运营变更 | 依赖管理员临时修改 | 成员交接、账号换绑、套餐变更、密钥轮换和暂停恢复全部留痕 | 客户使用期间的变化不破坏历史数据 |
| 客户退出 | 没有完整流程 | 身份确认、停止新任务、资产清点、数据包核验、保留期、正式删除和备份到期清除 | 客户可以安全退出并获得删除证明 |
| 小范围试用 | 目前只有内部用户 | 选择 1-3 家客户试用 30 天 | 验证产品、稳定性和收费方式 |

完整流程见 [客户开通运营变更与退出流程.md](./客户开通运营变更与退出流程.md)。

### AI 生图稳定性必须先治理

- 当前内部生图服务的概率性错误可能与服务器 VPN 或代理抖动有关，但必须通过 DNS、连接、TLS、上游受理、生成、下载分段监控确认。
- 生产 Provider 使用独立出口路由，不继续依赖服务器系统全局 VPN。
- 保存幂等键和上游任务 ID；本地失联但上游状态不明时先核验原任务，不能直接重提。
- 建立 Provider 健康评分、熔断和兼容路由切换，故障路由停止接收新任务。
- 生图成功后的下载、去水印和存储分开处理，后处理失败不能重新付费生成。
- 保存脱敏完整上游响应和费用状态，让 524 等错误可以确认真实原因及是否计费。

完整方案见 [账号数据采集与AI生图稳定性专项.md](./账号数据采集与AI生图稳定性专项.md)。

## 四、首批优先做什么

| 顺序 | 待办 | 完成标准 |
|---:|---|---|
| 1 | 确定第一版只卖哪些功能 | 有明确的包含和不包含清单 |
| 2 | 确定内容审核和自动发布边界 | 统一哪些内容必须人工审核、哪些客户可启用云手机自动发布 |
| 3 | 整理当前生产代码和数据库版本 | 线上版本可以追溯和回滚 |
| 4 | 设计企业、工作区和成员 | 多租户数据模型评审通过 |
| 5 | 列出所有数据表的企业归属 | 知道每张表如何隔离和迁移 |
| 6 | 设计统一任务中心 | 生图、采集、发布和报表使用同一套任务规则 |
| 7 | 完成生图稳定性第一阶段 | 能定位 VPN/代理、上游和下载故障，未知状态不盲目重提 |
| 8 | 完成账号采集状态与补采原型 | 每个账号有水位，任务中断后只补失败帖子 |
| 9 | 建立两个看板的指标说明和对账 | 每个指标都有来源、公式和验证结果 |
| 10 | 建立数据库、磁盘、任务队列告警 | 服务卡死前能够收到提醒 |
| 11 | 开始记录 AI 和工作流成本 | 任意任务能查到模型和供应商成本 |
| 12 | 打通内容生产到人工审核的原型 | 一条内容能生成、预审、驳回返工并审核通过 |
| 13 | 接通云手机发布接口原型 | 审核通过的内容能下发、执行、回传并进入数据复盘 |

## 五、最终应该变成什么样

```text
客户注册企业
  -> 邀请成员并分配角色
  -> 选择只用 AI 内容，或接入小红书数据
  -> 使用自己的云登环境、账号和手机完成授权
  -> 平台生成内容并进行机器预审
  -> 运营人员审核，不通过则返工
  -> 审核通过后调用客户云手机发布
  -> 云手机回传发布结果，平台继续采集数据和展示看板
  -> 所有操作都有记录
  -> 每月可以看到使用量、费用和数据导出
```
