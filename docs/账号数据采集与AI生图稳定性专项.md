# 账号数据采集与 AI 生图稳定性专项

更新日期：2026-08-07

## 一、专项目标

这两个问题不能继续依赖人工重跑：

1. 账号主页数据抓取要从“一次脚本执行”升级为持续采集系统，知道每个账号抓到哪里、缺了什么、为什么失败以及如何补齐。
2. AI 生图要从“调用某个接口并等待结果”升级为具备稳定出口、健康路由、状态核验、故障切换和成本保护的任务系统。

关于内部生图服务偶发报错，目前 VPN 或代理不稳定是高概率怀疑点，但在分段监控上线前不能当作已经证实的唯一根因。正式架构也不能继续依赖某台服务器的通用 VPN 是否在线。

## 二、账号数据抓取优化

### 1. 每个账号必须有独立采集状态

每个企业、账号和数据类型保存：

- 稳定账号 ID、当前环境/设备绑定和登录状态。
- 首次全量是否完成、最近一次完整成功时间和最近一次增量成功时间。
- 列表游标、时间水位、最近已见帖子 ID 和安全重叠窗口。
- 应采帖子数、已采帖子数、详情完成数、互动完成数和缺失数。
- 最近失败阶段、标准错误码、重试次数、执行 Agent/设备和证据。
- 下一次计划时间、是否暂停、是否需要登录或人工处理。

环境改名或删除不能删除账号和历史数据，只改变当前执行绑定。

### 2. 抓取任务拆成可恢复阶段

```text
父任务：同步账号数据
  -> 检查账号绑定与登录状态
  -> 抓主页基本信息
  -> 抓帖子列表并保存原始快照
  -> 识别新增、更新和疑似缺失帖子
  -> 并行抓每条帖子详情
  -> 抓互动及其他授权数据
  -> 幂等写入事实表
  -> 刷新日级聚合
  -> 执行数量与完整性校验
  -> 生成成功、部分成功和失败清单
```

父任务失败不应抹掉已成功子任务；重新执行时默认只补失败阶段和缺失帖子。

### 3. 全量、增量和补采使用不同策略

- **首次全量**：分页抓到明确结束条件，保存页数、帖子数和原始响应证据。
- **每日增量**：从水位向前保留安全重叠窗口，再按稳定帖子 ID 去重，避免置顶、删帖、排序变化造成漏数。
- **定期校准**：周期性回看最近一段时间，检测列表数量、帖子 ID 和互动数是否变化。
- **历史补采**：按账号和日期切片进入低优先级队列，不挤占当天增量。
- **失败补采**：只重跑登录、列表、详情、互动或落库中的失败阶段，不重新执行全部账号。

### 4. 原始数据、解析和落库分开

- 抓到列表或详情后先保存带时间和来源的原始快照，再进行解析。
- 解析规则升级后可以从原始快照重放，不必重新操作小红书页面。
- 事实表按企业、账号、帖子 ID、日期和数据类型使用幂等键更新。
- 同一任务重复回调或 Worker 重启不能产生重复帖子和重复互动。
- 原始层、事实层、聚合层和看板层均记录所属采集批次，支持四层对账。

### 5. 并发和调度策略

- 同一个账号同一时间只允许一个会改变游标的列表任务。
- 不同账号可以按 Agent、设备和云登环境并行，但要设置企业级和执行端级并发上限。
- 同一环境的主页、详情和发布操作必须使用冲突矩阵，不能互相抢占。
- 当天增量优先于历史补采，失败重试使用退避，登录失效立即暂停该账号而不是持续重试。
- 调度器根据上次成功时间、数据缺口、账号优先级和执行端健康分配任务。

### 6. 错误必须分类

| 类型 | 处理方式 |
|---|---|
| 登录失效、验证码、扫码挑战 | 账号暂停，创建登录任务，恢复后从断点继续 |
| 页面结构变化或元素缺失 | 保存截图和页面摘要，停止同版本批量重试并告警 |
| 网络、Agent 断线、浏览器崩溃 | 有限重试并迁移到健康执行端，保留已完成阶段 |
| 账号不存在、封禁或无权限 | 标记永久错误，等待人工确认，不无限重试 |
| 解析失败 | 保留原始快照，修正规则后离线重放 |
| 数据库写入或聚合失败 | 不重新抓页面，只重放保存的原始数据或事实数据 |

### 7. 准确性验收

- 每个账号显示数据截止时间、最近完整成功、缺失帖子和失败阶段。
- 随机抽取账号，与真实主页逐条比对帖子 ID、发布时间和数量。
- 同一天重复运行结果一致，不增加重复记录。
- 中途杀死 Worker 后可以恢复，已成功帖子不重新抓取。
- 连续约定周期达到账号覆盖率、准时率、完整率和对账差异目标后，运营看板才允许标记为正式可用。

## 三、AI 生图策略优化

### 1. 目标调用链

```text
用户提交
  -> 统一任务队列
  -> Provider 兼容性与配额检查
  -> 选择 Provider + 出口路由
  -> 请求受理并记录幂等键/上游任务 ID
  -> 轮询或等待回调
  -> 核验输出尺寸、格式和完整性
  -> 下载并转存到平台对象存储
  -> 返回平台稳定图片地址
```

前端断线、Web 服务重启、VPN 抖动或上游响应慢，都不能让任务从数据库消失。

### 2. 出口网络不再依赖通用 VPN

- 为每个 Provider 配置明确的出口模式：直连、专用代理、固定出口网关或备用出口。
- 生产 Worker 不跟随操作系统全局 VPN 自动切换，避免其他软件修改路由后影响任务。
- 对确需代理的上游使用独立、可监控、可切换的代理出口，优先使用稳定出口和固定公网 IP。
- 配置 Provider 域名白名单、DNS 解析策略、连接池和代理认证，禁止把密钥写入日志。
- 通用 VPN 只能作为应急方案，不能成为生产默认依赖。

### 3. 把故障拆成六段监控

每次请求记录并区分：

1. DNS 是否解析成功及耗时。
2. TCP/代理连接是否成功及耗时。
3. TLS 握手是否成功及耗时。
4. 上游是否受理请求、HTTP 状态和响应头耗时。
5. 生成任务轮询/回调状态及总耗时。
6. 结果图片下载、校验和转存是否成功。

只有这样才能确认问题到底在 VPN、Provider、生成模型、下载域名、对象存储还是本地 Worker。

### 4. 超时必须分层

- 连接超时：只约束 DNS、代理、TCP 和 TLS 建连。
- 请求响应超时：约束上游返回受理结果，不等于整张图片生成时间。
- 生成截止时间：约束上游任务最长允许运行时间。
- 轮询间隔和连续失败阈值：避免高频打上游。
- 下载超时：单独控制结果图片下载，并支持断点或重新下载同一结果。
- 平台任务总截止时间：超时后进入“待核验”，不能直接认定上游失败。

管理后台修改 Provider 超时后只影响新执行尝试；已经提交到上游的任务继续使用创建时的配置快照。

### 5. 不能盲目重试，先判断上游是否受理

| 场景 | 是否可以自动重提 |
|---|---|
| 建连失败，确认请求尚未发出 | 可以，有限退避重试 |
| 上游返回明确的临时错误且没有创建任务 | 可以按策略重试或切备用等价 Provider |
| 已获得上游任务 ID | 不重提，只轮询或查询原任务 |
| 本地超时但不确定上游是否受理 | 进入待核验，先按幂等键或请求 ID 查询 |
| 参数错误、鉴权错误、内容安全拒绝 | 不自动重试，直接给出可操作错误 |
| 图片生成成功但下载失败 | 不重新生图，只重新下载和转存原结果 |

这条规则用于避免同一张图被上游生成多次并重复计费。

### 6. Provider 健康、熔断和故障切换

- 按 Provider 和出口组合统计近窗口成功率、超时率、P95 耗时、429、5xx 和下载失败率。
- 连续网络错误或服务错误达到阈值后自动熔断，停止继续分配新任务。
- 半开状态用少量探测任务验证恢复，成功后逐步放量。
- 自动切换只允许在模型、尺寸、参考图、质量和计费规则兼容的路由之间进行。
- 替代 Provider 会改变模型效果或价格时，不静默切换；任务进入待确认或按企业预先配置的降级策略处理。
- Provider 恢复后不能瞬间回灌全部排队任务，需要渐进恢复并发。

### 7. 结果必须平台化保存

- 上游 URL 只作为临时来源，生成成功后立即转存企业对象存储。
- 下载后校验 MIME、文件头、尺寸、比例、文件大小和校验值，防止保存 HTML 错误页或半张图。
- 原图、去水印版本、缩略图和最终交付图使用不同对象版本，不互相覆盖。
- 去水印失败不能抹掉原图；按策略返回原图、进入重试或等待人工处理。
- 用户最终访问平台/CDN 地址，不直接依赖上游临时域名和用户侧网络是否能访问该域名。

### 8. 可观测性和错误展示

- 保存脱敏后的完整上游状态、响应体、请求 ID、Provider 任务 ID、出口路由和每阶段耗时。
- 前端错误显示标准错误类型、是否收费、是否自动重试、当前处理动作和建议，不只显示 524 或“生成失败”。
- 管理后台展示 Provider × 出口的实时健康、近 24 小时错误分布和正在熔断的路由。
- 对未知状态建立后台核验任务，最终归为成功、失败、已退款、可能重复计费或需人工处理。

## 五、上线顺序

1. 先加监控和状态记录，获得 VPN/上游/下载各自的真实错误占比。
2. 同时将账号采集和生图接入持久化统一任务中心，先解决任务丢失和无法恢复。
3. 生图启用独立出口、分层超时、幂等核验和结果转存。
4. 账号采集启用原始快照、增量水位、失败补采和完整性告警。
5. 再启用自动熔断、Provider 故障切换和多执行端动态调度。
6. 用网络断开、VPN 抖动、上游 5xx、下载失败、Worker 重启和登录失效进行故障演练后再正式开放。

最终验收不是“知道偶尔会报错”，而是每个错误都有证据、标准状态、自动处置、费用结论和人工兜底，账号数据也能证明没有因为失败重跑、排序变化或环境变更而漏采或重复。
