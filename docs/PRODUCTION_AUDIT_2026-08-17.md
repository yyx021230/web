# 生产环境审计与下次发布门禁（2026-08-17）

## 当前结论

线上核心服务当前可用，容器未出现持续重启，管理员、小红书运营、品牌负责人和投手的核心看板接口均通过真实身份冒烟。当前不建议立即发布完整新版本，必须先完成本页的 P0 门禁。

## 已确认的问题

### P0：发布前必须处理

1. PostgreSQL 当前约 19GB，其中 `ai_tasks` 约 15GB，主要是已结束任务仍保存参考图 base64/URL 导致的 TOAST 膨胀。继续累积会提高查询、备份和磁盘 IO 风险。
2. 当前没有可恢复的完整生产备份，也没有已安装的每日备份和健康监控计划任务。现有备份目录只有一次小型表级热修备份，不能作为整库回滚依据。
3. 线上 Compose 项目名为 `web`，数据卷为 `web_pgdata`、`web_redisdata`、`web_miniodata`。如果使用其他项目名启动，会创建空卷并表现为“数据全部消失”。
4. Windows 当前无法稳定拉取 Docker Hub，且新版本需要的 Python/Node 基础镜像未缓存。构建失败前不得停止任何线上服务。
5. 本地待上线迁移头为 `9c0d1e2f3a4b`，线上为 `4d5e6f7a8b9c`。必须先在生产备份副本演练完整迁移和回滚，不能直接在唯一生产库试迁移。

### P1：已在本地修复，待随新版本发布

1. 非管理员 AI 页面每 2 秒请求管理员全局队列接口，线上 15 分钟内产生过 589 次 `403`。新版本只允许管理员轮询全局队列，普通用户只查自己的任务。
2. 投流定时刷新每次删除并重写完整 30 天数据，产生大量 WAL；线上出现约 500MB 一轮的检查点写入，检查点可持续约 269 秒。新版本改为按键比较，只新增、更新变化行并删除真实失效行。
3. 投流刷新存在错误时仍显示“成功”，且有历史 `running` 记录永久悬挂。新版本增加 `partial` 状态及 12 小时超时收尾。
4. `dashboard_snapshots` 没有过期清理，当前约 117MB。新版本在写入快照时清理过期超过一天的记录。
5. 已结束 AI 任务继续保留大参考图。新版本在完成、失败、取消时自动移除大输入，但保留 Provider、上游任务 ID 和错误证据。
6. 生产源码中有约 1.1 万个 macOS `._*` 文件；发布包和部署脚本已排除并清理这些文件。
7. 旧前端镜像约 7.3GB。新 Dockerfile 使用 Next standalone，当前本地输出约 0.9GB，避免每次发布复制完整 `node_modules`。
8. 项目存在两个根路由，导致 Next standalone 构建追踪告警。废弃的后台根重定向已移除。

### 当前观察项

1. 最近 AI 上游偶发 `502/524` 或“未提供错误详情”。审计期间队列从空闲进入真实用户负载，数据库和 Redis 一致显示 6–10 个处理中任务，Worker 正常。这属于上游不稳定，不应通过盲目重复提交规避；需继续保留完整上游证据和未知结果对账。
2. 投流刷新最近每天仍有约 149–228 个子错误。新版本会标记为“部分成功”，上线后必须查看具体账户/报表错误，不能只看总任务终态。
3. 线上原始投流报表和聚合数据当前最新日期均为 2026-08-16，符合接口只能稳定刷新到前一天的现状。
4. 数据库中仍有旧角色值 `xhs_buyer`。当前服务会兼容归一化为 `buyer`，上线后应继续做角色矩阵冒烟，避免新代码直接按旧字符串判断。
5. `xhs_account_id` 的本地配置不会因数据库迁移自动进入线上。需要按稳定 `shop_id` 生成独立、可审计的配置补录清单，严禁复制本地数据库覆盖生产库。
6. 线上容器仍使用无版本标签的 `web-backend`、`web-frontend`、`web-ai-worker`，且旧后端没有 `/version`。新版本发布后必须用版本化镜像和发布清单，避免无法确认当前代码基线。
7. 最后 30 分钟日志中，主页同步有 3 个账号返回 0 篇，另有 1 个云登/MCP 主页接口在环境关闭阶段返回 `500`。现有保护逻辑保留了原帖子，未发生清空；任务仍需明确标为部分失败，并支持按失败账号重跑。
8. 同期核心容器重启次数均为 0，未发现 Web、Worker、PostgreSQL 或 Redis 崩溃循环。

## 强制上线顺序

1. 冻结提交窗口，确认数据库及 Redis 中 AI `queued/processing` 均为 0，确认没有正在执行的小红书同步、报表刷新、发布和 Dify 任务。
2. 在维护窗口部署或单独执行 AI 历史参数瘦身逻辑，分批清理终态任务的大输入字段。
3. 候选数归零后执行一次 `VACUUM (FULL, ANALYZE) ai_tasks`。此操作会锁表，必须在维护窗口执行并观察 C 盘空间。
4. 创建 PostgreSQL + uploads 全量备份到 D 盘，执行 `pg_restore -l` 校验，并在隔离数据库完成一次真实恢复演练。
5. 将精确版本的 Python/Node 基础镜像预先加载到 Windows；构建候选镜像成功前不得停止线上容器。
6. 在备份副本演练 `4d5e6f7a8b9c -> 9c0d1e2f3a4b`，核对行数、外键、唯一索引和迁移耗时。
7. 使用发布脚本部署，强制项目名为 `web`，并在启动前后比较 PostgreSQL 与 uploads 的实际挂载源。
8. 保持所有影子执行和 AI reconciliation 开关关闭，先完成登录、权限、AI、生图历史、图片访问、看板、同步、定时任务和发布链路冒烟。
9. 单独按 `shop_id` 补录并核对线上 `xhs_account_id`，不得把本地 SQLite/PostgreSQL 数据库带到线上。
10. 安装每日备份和 5 分钟健康监控，确认 `runtime/health/latest.json` 生成且状态为 `ok` 后才结束维护窗口。

## 回滚判定

出现以下任一情况立即停止扩大灰度并回滚应用：数据挂载源发生变化、迁移 revision 不一致、核心角色出现 `401/403/500` 回归、AI 队列无法恢复、图片路径大量 `404/5xx`、数据库连接或磁盘 IO 持续异常、定时任务重复触发。

数据库已迁移但应用需要回滚时，优先回滚应用并保留新增表；只有旧应用无法兼容新结构时，才使用已经恢复演练过的整库备份。禁止使用空卷、临时开发库或本地数据库覆盖生产。
