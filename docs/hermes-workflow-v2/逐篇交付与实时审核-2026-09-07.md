# 逐篇交付与实时审核

版本：`2026-09-07-progress-v2`，接续 `latency-v1`。

## 本次修复的断点

上一版只解决生产阶段的整批等待，没有解决结果回传：任务 #10 中 3 篇已通过图文检查，Web 仍是 0/4；因为 Worker 只在子进程全部结束后调用 complete 接口。

目标：每篇完整图文通过既有检查后，马上独立回传为“待审核”。其余帖子继续生产；用户可以先看、复制、编辑、通过或不通过已经回传的帖子。

## 数据链路

1. Producer：每篇 image/OCR 成功后，将所有已就绪图文写入本任务的原子 `progress.json`，不等待 render 或任务结束。仅上游生图完成、OCR 未通过的图片不提前交付。
2. Worker：生产中约每 2 秒检测快照；有变化就调用 `/api/v1/hermes-workflows/worker/runs/{run_id}/progress`，请求最长等待 5 秒。收到确认才记住快照摘要，断线保留快照并重试；不因此重生。
3. API：校验 Worker 所有权、账号和篇序号、车型、图文完整性与 hard_pass；只将对应帖子从生产中改为待审核。没有回传的帖子不判失败，不设置 finished_at，不把 Worker 提前变为空闲。
4. 前端：生产中的可见任务每 3 秒刷新详情，任务列表有活动任务时也每 3 秒刷新；空闲列表仍为 15 秒。隐藏页面暂停请求，详情请求完成后再安排下次刷新。沿用原卡片样式，逐篇显示待审核/生产中，并提示剩余篇数。
5. 最终回传：仍调用 complete 收尾，但不会覆盖提前交付的稿件、编辑版本、审核结果或发布排期。最终缺少一篇也不会把已经交付的其他篇降级。

正常本地链路通常数秒内可见，而不是毫秒级推送；网络故障会延后回传。未增加生图重试、未改变文案或图片提示词，也不自动审核和发布。

## 一致性保护

- API 条件更新只允许写入尚未交付的帖子，同一篇重复或迟到回传不覆盖首次交付及人工修改。
- 一批所有篇提前回传后仍保留生产 Worker 的内部任务占用，直到最终确认；用户可以提前审核。
- Worker 崩溃重新领取时，只把未完成帖子恢复为生产中，不重置已交付内容。
- 接口拒绝错误 Worker、非本任务账号/序号、重复条目、不完整图文或错误车型；一组回传不合法时整组回滚。

## 验证与部署边界

- API 测试：包括部分交付立即可读、幂等、提前编辑审核后最终回传不覆盖、全量提前审核后正常收尾、最终失败只影响未完成篇。
- 前端测试：模拟 0/2 到 1/2，确认已完成卡片显示图片、完整文案及审核按钮，另一篇仍显示生产中；不需刷新整个页面。
