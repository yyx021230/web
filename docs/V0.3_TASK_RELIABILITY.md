# v0.3 Task Reliability

This release is being implemented in isolated steps. Existing production task paths remain unchanged until their adapters pass dedicated regression tests.

## Step 1: Durable Job Kernel

Status: complete locally, not deployed.

- `jobs`: ownership scope, idempotency, status, progress, retries, lease metadata, result summary, and errors.
- `job_items`: per-account or per-input batch outcomes.
- `job_attempts`: worker execution attempts and heartbeat metadata.
- `job_events`: append-only task state and operator events.
- State flow: `queued -> leased -> running`, with explicit review, retry, success, failure, cancellation, and dead-letter outcomes.
- Service methods flush but do not commit, so business writes and task events can share one transaction.
- Idempotent inserts use native PostgreSQL/SQLite conflict handling.

## Step 2A: Atomic Worker Claiming

Status: complete locally, not deployed.

- Workers atomically claim one eligible queued job using `UPDATE ... RETURNING`.
- PostgreSQL claims use `FOR UPDATE SKIP LOCKED`; SQLite uses an atomic scalar-subquery update.
- Lower priority numbers run first, followed by creation time and job ID.
- Claims filter worker type, optional job types, cancellation state, and `run_after`.
- A successful claim writes the lease, first heartbeat, `job_attempts` row, and transition event in one caller-owned transaction.
- Rollback releases the claim without leaving an attempt or event behind.

## Step 2B: Worker Start and Lease Heartbeats

Status: complete locally, not deployed.

- Only the worker that owns the active `job_id + attempt_id` lease can start or renew a job.
- Starting a claimed job atomically moves both the job and its attempt from `leased` to `running`.
- Duplicate start calls are idempotent and record only one `leased -> running` event.
- Heartbeats renew both records without writing high-volume events.
- Out-of-order and concurrent heartbeats cannot move timestamps backward or shorten an existing lease.
- Expired leases, stale attempt IDs, and incorrect worker IDs are rejected without partial updates.
- Start and heartbeat writes remain in the caller-owned transaction and roll back together.

## Step 2C: Lease Recovery and Bounded Retries

Status: complete locally, not deployed.

- Expired `leased/running` jobs are recovered atomically in bounded batches.
- PostgreSQL recovery uses `FOR UPDATE SKIP LOCKED`; SQLite uses conditional `UPDATE ... RETURNING` statements.
- Pending cancellation wins over retry and does not consume a retry attempt.
- Recoverable jobs enter `retry_wait`; due retries are atomically released back to `queued`.
- Jobs that exceed `max_retries` enter `dead_letter` and cannot be claimed again.
- The expired attempt is finalized as `failed` or `cancelled`, while its heartbeat and lease timestamps remain available for audit.
- Job-level stale errors are cleared when a replacement worker claims the retry; attempt and event history remains intact.
- Concurrent recovery/release calls record one transition, and all recovery writes follow the caller transaction.

## Step 3A: Homepage Sync Shadow Adapter

Status: complete locally, disabled by default, not deployed.

- Manual homepage-post sync and failed-account reruns continue to execute exclusively through the existing executor.
- The adapter mirrors the legacy batch and account outcomes into `jobs` and `job_items`; it never calls Xiaohongshu, MCP, a browser, or a worker.
- Shadow jobs use `worker_type=legacy_shadow`, so existing server workers cannot claim or execute them.
- `XHS_HOMEPAGE_SYNC_SHADOW_ENABLED=false` is the default. Enabling it changes observability only, not execution ownership.
- Request parameters, requesting user, source run, retry parent, per-account status/result/error, progress, and terminal metrics are copied into the durable records.
- Writes run in an independent best-effort transaction. A shadow database or parity failure is logged and cannot fail the legacy sync task.
- Job and account inserts are idempotent under repeated and concurrent callbacks.
- Only account-level phases are mirrored. Per-note progress is deliberately excluded to avoid adding high-frequency database I/O.
- Terminal parity compares legacy in-memory status, legacy history status, durable job status, and successful-account totals.
- The existing queued-cancellation path can leave the legacy history row queued; the adapter records this as a parity mismatch instead of hiding it.

Migration gate:

1. Deploy with the feature flag disabled and verify the schema/runtime baseline.
2. Enable the flag in a controlled environment and collect manual-sync plus failed-rerun samples.
3. Require matched terminal status and account totals, with no duplicate execution or material latency increase.
4. Resolve known legacy mismatches before changing execution ownership.
5. Migrate homepage sync to a real durable worker in a separate change with rollback support.

## Step 3B: Homepage Shadow Parity Review

Status: complete locally, not deployed.

- Added the admin-only read endpoint `GET /api/v1/admin/reliability/xhs-homepage-shadow`.
- The report starts from terminal legacy runs, then independently reloads durable jobs/items instead of trusting the parity value stored by the shadow writer. A completely missed shadow write therefore remains visible.
- It compares terminal status, requester, request snapshot, source, retry parent, task timestamps/errors/cancellation, progress totals, summary counts, and every account status/result/error/timestamp.
- Missing shadow jobs, duplicate shadow jobs, orphan shadow jobs, invalid source IDs, missing/extra account items, altered payloads, broken retry parents, and field-level drift are returned as explicit mismatch codes.
- Filters support terminal time range, sample limit, and required minimum samples. Reversed ranges and impossible sample gates are rejected.
- The report uses five fixed batch queries when no retry-parent lookup is needed; the query count does not grow with the number of runs or accounts.
- Mismatch details are capped per sample, while aggregate reason counts still show the complete affected categories.
- Gate decisions are `insufficient_samples`, `blocked_by_mismatch`, or `manual_validation_required`.
- `execution_cutover_allowed` remains false even when automated parity passes. Duplicate-execution, latency/load, cancellation, and failed-rerun behavior still require controlled runtime validation.
- A parity test exposed and fixed terminal cancellation replay losing `started_at`; started cancellations now replay through `leased -> running -> cancelled`, while never-started queued cancellations still terminate directly.

## Step 4A: AI Image Shadow Lifecycle

Status: complete locally, disabled by default, not deployed.

- Added `AI_IMAGE_SHADOW_ENABLED=false`. The existing Redis worker and `ai_tasks` table remain the only execution path; durable jobs use `worker_type=legacy_shadow` and cannot be claimed by normal workers.
- One legacy AI task maps idempotently to one `ai_image_generation` durable job. The shadow request snapshot records dimensions, style, quality, count, reference presence, model, prompt hash, and prompt length without copying prompts, base64 reference images, Provider keys, or authorization data.
- The lifecycle records queueing, worker start, upstream start, Provider selection, upstream completion, platform storage, watermark completion, and terminal outcome. Status transitions and a bounded phase history remain available for audit.
- Explicit upstream failures map to `failed`; successful tasks map to `succeeded`; queued or running cancellation maps to `cancelled`.
- Platform deadline expiry, stale-processing cleanup, and worker restart recovery are conservatively marked `waiting_review` with `upstream_result_unknown`, because the upstream may already have accepted and charged the request.
- With shadow mode disabled, the legacy restart behavior remains unchanged. With shadow mode enabled, an interrupted processing task is no longer automatically requeued when its upstream result may be unknown; it remains available for reconciliation instead of risking a duplicate paid request.
- Shadow writes use independent best-effort transactions. A shadow database failure is logged and cannot fail submission, Provider execution, cancellation, or legacy task recovery.
- Step 4A records lifecycle evidence only. Upstream-ID capture and reconciliation are implemented separately in Step 4B so they can remain disabled during the initial shadow rollout.

## Step 4B: AI Image Upstream Reconciliation

Status: complete locally, disabled by default, not deployed.

- MentalOut batch and legacy batch adapters persist an upstream task ID immediately after upstream acceptance, before polling for completion. Provider ID/kind/model, query capability, and acceptance time are stored as a bounded, deduplicated attempt list in both the legacy task and its shadow job.
- Provider selection and upstream acceptance use cancellation-safe independent transactions. A platform timeout or worker cancellation therefore cannot erase the evidence needed to query the already accepted request.
- Startup recovery checks `AI_IMAGE_SHADOW_ENABLED`. When enabled, interrupted processing tasks with uncertain outcomes move to `waiting_review` instead of being submitted again. When disabled, legacy behavior remains unchanged for a safe rollout.
- Automatic reconciliation performs status-only queries against accepted task IDs and never calls an upstream create/generate endpoint. Completed images are recovered into platform storage when possible; confirmed failures close the task; generating, unknown, and unsupported outcomes remain in review with bounded exponential backoff.
- Multiple accepted attempts are all retained. The job remains in review until every attempt has a terminal result, then records duplicate-success and duplicate-charge risk instead of hiding it.
- Missing or non-queryable task IDs require explicit manual review. Repeated checks are idempotent and do not duplicate the manual-required audit event.
- The AI worker can run reconciliation ticks only when both `AI_IMAGE_SHADOW_ENABLED=true` and `AI_IMAGE_RECONCILIATION_ENABLED=true`. Interval and batch size are controlled by `AI_IMAGE_RECONCILIATION_INTERVAL_SECONDS` and `AI_IMAGE_RECONCILIATION_BATCH_SIZE`.
- Every candidate is processed in its own transaction. One Provider outage or malformed task cannot roll back or block other reconciliation jobs in the same tick.
- Admin-only endpoints expose safe metadata without prompts or Provider keys:
  - `GET /api/v1/admin/reliability/ai-image-shadow`
  - `POST /api/v1/admin/reliability/ai-image-shadow/{job_id}/reconcile`
  - `POST /api/v1/admin/reliability/ai-image-shadow/{job_id}/resolve` with `outcome` and a required audit `reason`

Rollout gate:

1. Deploy with both AI flags disabled and verify that existing generation behavior is unchanged.
2. Enable only shadow mode for a controlled sample; verify phase coverage and upstream-ID capture.
3. Review `waiting_review` records manually and compare Provider status before enabling the automatic loop.
4. Enable reconciliation for a small worker batch, monitor query errors, recovered images, unknown results, and duplicate-charge risk.
5. Keep execution ownership on the legacy Redis worker until reconciliation evidence and operational runbooks are stable.

## Step 5A: Unified Task-Center Read API

Status: complete locally, not deployed.

- Added admin-only read endpoints:
  - `GET /api/v1/admin/reliability/jobs`
  - `GET /api/v1/admin/reliability/jobs/{job_id}`
- The list supports status, job type, worker type, user/display name, task ID, source ID, step, and error-code filtering with bounded pagination.
- Summary cards are calculated independently of the selected status so operators can switch status views without losing the surrounding workload totals.
- The detail view exposes job progress, parent/child links, batch items, execution attempts, and the append-only event timeline.
- Prompts, reference-image data, base64 content, API keys, passwords, cookies, authorization headers, Provider tokens, and signed URL credentials are omitted or redacted before leaving the backend.
- Internal exception text is not exposed. Public user messages are also scanned for Bearer tokens and inline secret assignments.
- Large JSON values and evidence collections are bounded. Truncation is reported explicitly and does not issue per-item database queries.
- The existing `/admin/tasks` page now opens on a read-only `可靠任务` tab while retaining the legacy workflow and AI task tabs.
- This step adds observability only. It does not cancel, retry, claim, execute, or delete durable jobs and does not change any legacy execution owner.

## Step 5B: Xiaohongshu Report Refresh Shadow and Parity

Status: complete locally, disabled by default, not deployed.

- Added the persistent `xhs_report_refresh_runs` history for manual report refreshes and the configured `ad_data_refresh` scheduled task. Each batch stores a bounded request snapshot, per-report totals, terminal status, timestamps, and links to the requester or schedule run.
- Added `XHS_REPORT_REFRESH_SHADOW_ENABLED=false`. When disabled, the existing in-memory manual task and scheduled refresh paths have no new database writes or response changes.
- When enabled, one legacy refresh batch maps idempotently to one `xhs_report_refresh` durable shadow job and one item per selected report type. Shadow jobs use `worker_type=legacy_shadow`, so normal workers cannot claim them.
- The existing `XHSService.refresh_jg_report_cache` calls remain the sole executor and keep their original order. The adapter never calls a report API and therefore cannot duplicate report downloads, database aggregation, or upstream load.
- Shadow callbacks use independent best-effort transactions. History or durable-job failures are logged and cannot fail the existing manual or scheduled refresh.
- Stored request fields are allowlisted to report type, account, date range, and bounded day count. API keys, tokens, raw report rows, and unbounded upstream responses are not copied into the history or job payload.
- Added the admin-only read endpoint `GET /api/v1/admin/reliability/xhs-report-refresh-shadow`. It independently compares terminal history runs with jobs and report items, detects missing, duplicate, orphaned, or altered shadows, and uses a fixed five-query plan for populated samples.
- Automated parity can end in `insufficient_samples`, `blocked_by_mismatch`, or `manual_validation_required`. `execution_cutover_allowed` always remains false until controlled runtime checks confirm one upstream execution per report type and acceptable database load.
- This step deliberately excludes refreshes performed internally by the scheduled report-publishing fallback. Those remain on the unchanged legacy path until they receive their own bounded execution identity and parity coverage.

Rollout gate:

1. Apply the migration and deploy with `XHS_REPORT_REFRESH_SHADOW_ENABLED=false`.
2. Enable the flag for a controlled set of manual and configured scheduled refreshes.
3. Require no missing, duplicate, orphaned, or field-level parity mismatches across the agreed sample window.
4. Verify upstream call counts, refreshed row/account totals, execution duration, and database I/O against the existing dashboard cache.
5. Keep the legacy refresh executor until a separate worker-cutover change supplies rollback and production evidence.

## Step 5C: Dify Workflow Task Shadow and Parity

Status: complete locally, disabled by default, not deployed.

- Added `DIFY_TASK_SHADOW_ENABLED=false`. User and admin workflow endpoints continue to create and execute the existing `dify_tasks`; the adapter only mirrors lifecycle evidence and never calls, polls, stops, or retries Dify.
- One legacy Dify task maps idempotently to one `dify_workflow` durable shadow job. Shadow jobs use `worker_type=legacy_shadow`, so normal workers cannot claim or execute them.
- The request snapshot stores workflow/user/task IDs plus input field names and top-level types. It never copies prompt text, file data, input values, API keys, authorization data, or output content.
- Queueing, start, completion, failure, cancellation, progress, upstream task ID, elapsed time, and output shape are mirrored in independent best-effort transactions. A shadow failure is logged and cannot fail the existing workflow request.
- Terminal durable state is immutable. If a cancelled legacy task later becomes successful, the adapter preserves the cancellation evidence and the parity report exposes the late-success drift instead of silently rewriting history.
- Deleting a terminal legacy task keeps its durable audit record, changes the source to `dify_task_deleted`, and appends a `legacy_source_deleted` event. Deleted snapshots are reported separately rather than being misclassified as orphan jobs.
- Added the admin-only read endpoint `GET /api/v1/admin/reliability/dify-task-shadow`. It independently compares terminal legacy tasks with durable jobs and detects missing, duplicate, orphaned, altered, or cancellation-drifted records with a fixed five-query plan for populated samples.
- Gate decisions are `insufficient_samples`, `blocked_by_mismatch`, or `manual_validation_required`. `execution_cutover_allowed` always remains false because Web-process restart recovery and upstream cancellation semantics are not yet owned by the durable worker.

Rollout gate:

1. Deploy with `DIFY_TASK_SHADOW_ENABLED=false` and verify the existing user/admin workflow behavior.
2. Enable the flag for controlled workflows and require exactly one Dify run call per legacy task.
3. Collect terminal parity samples with no missing, duplicate, orphaned, or field-level mismatch.
4. Restart the Web process with queued and running tasks, then review legacy stuck-task behavior without resubmitting work.
5. Test cancellation followed by a late upstream success or charge; keep execution ownership on the legacy path until a durable Dify worker and explicit reconciliation policy are available.
