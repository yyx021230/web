# 版本管理规范

## 仓库边界

- Git 只保存源码、数据库迁移、测试、部署配置模板和必要文档。
- 不保存 `.env`、Cookie、API Key、数据库文件、数据库备份、上传文件、运行日志、生成结果和编译产物。
- `package-lock.json` 必须提交，用于保证本地、Windows 和容器安装相同依赖。
- 线上数据库和本地数据库严格分离，部署不得覆盖线上数据卷和环境变量。

## 分支

- `main`：可部署的稳定版本，只合入已经验证的改动。
- `feature/<name>`：新功能。
- `fix/<name>`：缺陷修复。
- `perf/<name>`：性能优化。
- `release/<version>`：发布前集中验证。
- Codex 自动开发分支使用 `codex/<name>`。

禁止直接在 `main` 上进行未验证的大规模开发。一个任务使用一个分支，验证后再合并。

## 提交

提交信息采用：

```text
feat: 新增投流数据聚合
fix: 修复主页帖子增量同步
perf: 优化看板查询磁盘 IO
docs: 更新部署说明
chore: 调整构建配置
```

每次提交只包含一个可说明、可测试、可回滚的改动。禁止把数据库、密钥、临时文件和无关改动混进提交。

## 发布

1. 从 `main` 创建发布分支并完成迁移、后端测试、前端类型检查和关键业务回归。
2. 记录数据库迁移、环境变量变更、Windows 部署步骤和回滚步骤。
3. 合并到 `main` 后创建语义化标签，例如 `v0.1.0`。
4. Windows 只部署明确的 Git 提交或标签，不再部署无法追溯的本地目录快照。
5. 发布失败时回滚代码版本；数据库只执行已经验证的向前迁移或配套回滚方案。

## 日常检查

提交前至少执行：

```bash
git status --short
git diff --check
```

根据改动范围继续执行后端测试、前端类型检查和构建。提交前再次确认没有 `.env`、Cookie、Token、数据库和大文件。
