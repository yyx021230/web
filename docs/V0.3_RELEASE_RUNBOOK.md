# v0.3.x 任务可靠性发布手册

更新日期：2026-09-09

版本身份、唯一发布入口、不可变镜像、受控启动与回滚规则以
[Web 生产版本与发布规范](./RELEASE_VERSION_STANDARD.md) 为准。该规范属于强制门禁，优先级高于本手册中的操作示例。

生产现状、已确认风险和本次发布的强制前置顺序见
[生产环境审计与下次发布门禁](./PRODUCTION_AUDIT_2026-08-17.md)。该门禁优先级高于本手册中的通用步骤。

## 1. 版本定位

v0.3.x 建立统一持久任务内核、任务证据、影子对账、AI 未知结果恢复和数据库调度 Leader。现有 AI、Dify、小红书同步和报表执行路径默认保持不变，先旁路收集真实证据，再决定是否迁移执行权。

本地代码完成不代表已经通过生产门禁。禁止为了“看起来完成”直接打开所有开关，也禁止把小红书发布接到通用自动重试；发布必须先采用独立的发布订单、执行尝试和审核版本模型。

## 2. 本版本包含

- `jobs`、`job_items`、`job_attempts`、`job_events` 持久任务模型。
- 原子领取、租约、心跳、超时回收、有界重试、取消优先和死信。
- AI 生图生命周期影子记录、未知结果自动查询和管理员人工裁决。
- 主页、互动、详情、投流报表、Dify 的旁路影子记录与独立对账。
- 管理后台统一任务列表、证据详情、执行尝试和事件时间线。
- 数据库调度 Leader，避免多个 API 实例重复运行定时循环。
- 空 SQLite 数据库完整升级、降级、再升级回归。

本版本不包含：旧业务执行器的生产切换、通用发布重试、任务通知、多租户任务隔离。它们必须在真实影子数据通过门禁后继续实施。

## 3. 默认安全配置

首次发布必须显式保持：

```dotenv
AI_IMAGE_SHADOW_ENABLED=false
AI_IMAGE_RECONCILIATION_ENABLED=false
XHS_HOMEPAGE_SYNC_SHADOW_ENABLED=false
XHS_ENGAGEMENT_DETAIL_SYNC_SHADOW_ENABLED=false
XHS_REPORT_REFRESH_SHADOW_ENABLED=false
DIFY_TASK_SHADOW_ENABLED=false
SCHEDULER_LEADER_ENABLED=true
SCHEDULER_LEADER_LEASE_SECONDS=30
SCHEDULER_LEADER_HEARTBEAT_SECONDS=10
```

创作者中心互动同步需要在生产 `backend/.env` 中同时配置以下四项；只写在
项目根目录 `.env` 不会被应用加载：

```dotenv
SMS_CODE_CENTER_OPEN_API_CLIENT_ID=<签名客户端 ID>
SMS_CODE_CENTER_OPEN_API_CLIENT_SECRET=<签名客户端密钥>
SMS_CODE_CENTER_ADMIN_USERNAME=<手机云控管理员账号>
SMS_CODE_CENTER_ADMIN_PASSWORD=<手机云控管理员密码>
```

Windows 云登浏览器导出文件时，宿主机路径与容器路径必须同时可解析。生产根目录
`.env` 必须设置 `UPLOADS_HOST_PATH`：

```dotenv
UPLOADS_HOST_PATH=C:\projects\web\uploads
```

Compose 提供当前 Windows 部署目录的 MCP 双路径默认值。若上传目录迁移到 D 盘，
必须在根目录 `.env` 中同步覆盖以下三项：

```dotenv
UPLOADS_HOST_PATH=D:\ztqc-data\uploads
XHS_MCP_BROWSER_DOWNLOAD_DIR=D:\ztqc-data\uploads\mcp-downloads
XHS_MCP_CONTAINER_DOWNLOAD_DIR=/app/uploads/mcp-downloads
```

后端启动 MCP 时会派生以下双路径，禁止把容器内 `/tmp` 路径传给 Windows 浏览器：

```text
浏览器写入：C:\projects\web\uploads\mcp-downloads
容器读取：/app/uploads/mcp-downloads
```

发布后必须检查容器环境包含 `XHS_MCP_BROWSER_DOWNLOAD_DIR` 和
`XHS_MCP_CONTAINER_DOWNLOAD_DIR`，并确认日志中的“创作中心导出下载目录”同时显示
Windows 路径和 `/app/uploads/mcp-downloads`。故障案例和验证命令见
[`PRODUCTION_INCIDENTS.md`](./PRODUCTION_INCIDENTS.md)。

发布后必须在 backend 容器内只检查四项是否为非空，不输出具体密钥。

影子开关只增加观察记录，不应增加一次上游调用。AI reconciliation 只有在已确认 Provider 状态查询不会重复计费后才能启用。

## 4. 发布前门禁

先生成并校验生产 MCP。禁止直接把 macOS 本机构建产物打进 Linux 容器：

```bash
cd /Users/yyx/ztqc/cc_kaiyuan/claude-code-main/xiaohongshu-mcp-patched
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o /tmp/xiaohongshu-mcp-linux .
file /tmp/xiaohongshu-mcp-linux | grep -F "ELF 64-bit LSB executable, x86-64"
shasum -a 256 /tmp/xiaohongshu-mcp-linux
install -m 755 /tmp/xiaohongshu-mcp-linux /Users/yyx/ztqc/web/backend/bin/xiaohongshu-mcp
```

随后执行应用门禁：

```bash
cd /Users/yyx/ztqc/web
python3 scripts/check_alembic_heads.py
python3 scripts/check_tracked_secrets.py
cd backend
.venv/bin/pytest -q --cov=app --cov-branch --cov-report=term
cd ../frontend
npm run test:coverage
npm run type-check
npm run build
cd ..
git diff --check
```

必须满足：

- `backend/bin/xiaohongshu-mcp` 必须是 Linux x86_64 ELF；Mach-O、PE/Windows 或其他架构
  一律禁止进入发布包。后端镜像构建必须通过 Dockerfile 内的二次架构校验。
- 候选后端镜像必须执行 `/app/bin/xiaohongshu-mcp -h`，并用独立端口启动后确认
  `/health` 返回 `healthy`；不能只检查文件存在或执行权限。
- 后端全量测试必须通过，应用分支覆盖口径总覆盖率不得低于 70%。
- 前端 `18 passed`，纳入门禁的核心模块语句/行/函数覆盖率不得低于 75%，分支覆盖率不得低于 65%。
- 发布初始化 7 个场景全部通过：显式管理员、登录/RBAC、缺失凭据无脏数据、重复执行、残缺库修复、重置保留用户、账号冲突拒绝。
- 可靠性接口异常契约全部通过：影子对账校验、AI 对账 `400/404/409`、空 Leader 租约与非管理员拒绝均不得退化为 `500`。
- 新迁移数据库跨模块冒烟通过：初始化、认证、素材/模板、项目 CRUD、AI、工作流、车型、文案、提示词、小红书、后台与任务证据接口。
- 前端测试、类型检查和生产构建依次通过，生产构建生成 35 个路由；禁止并行运行 `type-check` 与 `build`，避免竞争写入 `.next/types`。
- 空 SQLite 数据库能 `upgrade head -> downgrade base -> upgrade head`。
- Alembic `head` 必须覆盖当前 ORM 的全部表和字段，禁止模型字段领先于迁移。
- v0.3 PostgreSQL 增量迁移可从 `4d5e6f7a8b9c` 生成到 `head`。
- 发布 commit、版本号和发布包一致，工作区不包含未提交业务修改；已发布过的版本号不得复用。
- 生产 AI、Dify、小红书同步、报表和发布任务全部排空。
- Compose 项目名必须锁定为 `web`，并记录发布前 PostgreSQL、Redis、MinIO 和 uploads 的实际挂载源。
- 精确版本的 Python/Node 基础镜像已在 Windows 缓存，候选镜像构建成功前不得停止生产服务。
- 已完成 AI 历史大字段清理和 `ai_tasks` 空间回收，C 盘满足“数据库大小 + 8GB”安全余量，D 盘不少于 20GB。
- 已生成可验证的 PostgreSQL + uploads 全量备份，并在隔离数据库完成真实恢复演练。

## 5. 生产发布顺序

1. 暂停新的重任务提交，确认 AI、Dify、同步、报表和发布任务全部排空。
2. 完成终态 AI 参数瘦身，并在维护窗口执行 `VACUUM (FULL, ANALYZE) ai_tasks`。
3. 执行数据库与上传目录全量备份，并在隔离数据库完成恢复演练。
4. 在生产备份副本执行 `alembic upgrade head`，确认 revision 为 `9c0d1e2f3a4b`。
5. 检查新增任务可靠性、报表刷新、调度租约、账号 ID 和创作者中心主数据结构。
6. 预先加载基础镜像并完成候选镜像构建，确认 Compose 项目仍为 `web`、数据挂载源不变。
7. 保持所有影子和 reconciliation 开关关闭，发布应用容器。
8. 验证 `/version`、`/health/ready`、登录、生图、工作流、同步、报表、看板和发布原路径。
9. 验证 `/api/v1/admin/reliability/scheduler-leader` 只有一个健康 owner，心跳持续前进。
10. 安装并验证每日备份与健康监控，观察至少一个完整定时周期，确认任务触发数量没有翻倍。

## 6. 灰度顺序

每次只启用一个观察能力，收集足够样本后再进入下一项：

1. `XHS_HOMEPAGE_SYNC_SHADOW_ENABLED`
2. `XHS_ENGAGEMENT_DETAIL_SYNC_SHADOW_ENABLED`
3. `XHS_REPORT_REFRESH_SHADOW_ENABLED`
4. `DIFY_TASK_SHADOW_ENABLED`
5. `AI_IMAGE_SHADOW_ENABLED`
6. `AI_IMAGE_RECONCILIATION_ENABLED`

每次改动后至少验证：上游调用次数没有增加、原业务结果不变、影子任务不可被普通 Worker 领取、终态和子项对账一致、数据库写入和耗时在可接受范围。

## 7. 对账入口

- 统一任务：`GET /api/v1/admin/reliability/jobs`
- 主页同步：`GET /api/v1/admin/reliability/xhs-homepage-shadow`
- 互动/详情：`GET /api/v1/admin/reliability/xhs-account-data-shadow?sync_kind=engagement|details`
- 报表刷新：`GET /api/v1/admin/reliability/xhs-report-refresh-shadow`
- Dify：`GET /api/v1/admin/reliability/dify-task-shadow`
- AI 待确认结果：`GET /api/v1/admin/reliability/ai-image-shadow`
- 调度 Leader：`GET /api/v1/admin/reliability/scheduler-leader`

对账必须独立读取旧记录和 durable 记录，不能只相信影子写入时生成的摘要。出现 missing、duplicate、orphan、altered、parent drift 或 cancellation drift 时，立即停止扩大灰度。

## 8. 执行权切换门禁

只有同时满足以下条件，后续版本才允许把某一种任务切给 durable worker：

- 控制样本中旧记录与影子记录无缺失、重复、孤儿或字段差异。
- 人工取消、进程重启、Worker 崩溃、网络超时和 Provider 迟到结果均已演练。
- 重复点击、调度重入和租约过期不会产生第二次上游副作用。
- 失败重试能区分临时错误、永久错误和需人工处理。
- 有单独的关闭开关和回到旧执行器的步骤。
- 数据库、Redis、上游调用次数、耗时和磁盘 IO 没有明显回归。

小红书发布不适用通用门禁。发布必须使用审核版本锁、发布订单、发布尝试、平台帖子事实和人工处理状态，且默认不自动重试未知结果。

## 9. 回滚

出现业务回归时先关闭对应影子或 reconciliation 开关；影子记录失败不应影响旧任务。调度 Leader 异常时只允许在确认单 API 实例后临时设置 `SCHEDULER_LEADER_ENABLED=false`。

应用回滚按 [v0.2.0 发布与恢复手册](./V0.2_RELEASE_RUNBOOK.md) 使用版本包和发布前备份，不使用 `git reset --hard`。如果新版本已经写入 v0.3 新表，优先回滚应用并保留新增审计数据；只有数据库结构本身阻塞旧应用时才执行数据库恢复。

## 10. 完成判定

v0.3.x 可标记“本地发布候选”需要：代码、迁移、632 个后端测试、后端应用分支覆盖口径总覆盖率不得低于 70%、18 个前端测试、前端覆盖率门槛、类型检查、生产构建和文档全部通过。

v0.3.x 可标记“生产验收完成”还需要：Windows 备份副本迁移、双 API Leader 演练、各影子流真实样本对账、AI 未知结果演练和完整业务冒烟。未完成这些生产步骤时，状态必须显示为“本地完成，待生产灰度”，不能写成“执行迁移已完成”。
